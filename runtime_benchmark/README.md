# runtime_benchmark

Compares answer **quality** and **performance** (TTFT, decode tok/s) between
two runtimes on the same QAIRT model bundle:

- **geniex** — this repo's plugin, driven through the
  [`auto_llm`](../examples/auto_llm/README.md) example
  (`build/bin/Release/auto_llm.exe`). Invoked once in `--batch-file` mode so
  the bundle is loaded a single time and reused across every prompt, with the
  KV cache reset between prompts so each answer is independent.
- **genie-t2t-run** — Qualcomm QAIRT SDK reference runner. One subprocess per
  prompt (it has no batch mode).

Both sides point at the **same bundle directory** and see the same prompts and
the same system message, so quality differences reflect the runtime, not the
inputs. The geniex side renders the bundle's own Jinja `chat_template` from
`tokenizer_config.json`; genie-t2t-run does no templating at all, so it is fed
an equivalent hand-built prompt string (see
[RUN_BENCHMARK.md § Chat templates](RUN_BENCHMARK.md#chat-templates)).

> **History.** This suite previously lived in the `nexa-sdk` repo as
> `tools/runtime_benchmark/`, where the geniex side ran **in-process** via the
> `geniex` Python package and located models in the `~/.cache/geniex` model
> cache. In this repo there is no Python binding and no model cache, so the
> geniex side is now a subprocess over `auto_llm.exe` and the model is named by
> its **bundle directory** (`--model-dir`). The runs under `results/` were
> collected with the old harness — see [Prior runs](#prior-runs).

## Workflow

The benchmark splits into two halves:

1. **On the Snapdragon device** — build `auto_llm`, run the prompt suite,
   collect raw answers. See [RUN_BENCHMARK.md](RUN_BENCHMARK.md). Since this
   repo *is* the runtime, this is usually the same ARM64 Windows dev box you
   build on; a remote Qualcomm QDC device works identically.
2. **On any machine, in Claude Code** — score the answers against the rubric,
   emit the final CSV. See [SCORE_WITH_CLAUDE.md](SCORE_WITH_CLAUDE.md).
   Scoring reads only the collected JSON, so it needs no NPU.

When **only plugin code has changed** (the bundle on disk is unchanged), pass
`--skip-genie` on step 1 to skip the genie-t2t-run pass — genie's answers for a
given bundle are deterministic, so you can reuse the genie answers from the
prior full run. The script writes the new geniex-only results to
`results/<slug>_geniex_only.csv`, and the scoring agent merges them with the
prior `<slug>.answers.json` to produce a fresh scored CSV. See
[RUN_BENCHMARK.md § Geniex-only re-runs](RUN_BENCHMARK.md#geniex-only-re-runs)
and
[SCORE_WITH_CLAUDE.md § Shape B](SCORE_WITH_CLAUDE.md#shape-b--geniex-only-re-run-paired-with-a-prior-full-run).

## Files

```
runtime_quality_benchmark.py   # collection script (runs on the device)
testing_prompts.md             # 100-prompt suite, grouped by category
scoring_rubric.txt             # 0/2/7/10 rubric reference
results/                       # all generated artifacts
RUN_BENCHMARK.md               # how to do step 1
SCORE_WITH_CLAUDE.md           # how to do step 2
```

## Quick start

```pwsh
# 1. Build the runtime driver (once per plugin change).
cmake --build build --config Release --target auto_llm -j32

# 2. Collect answers (from this directory).
$env:PYTHONIOENCODING = "utf-8"
python runtime_quality_benchmark.py --model-dir ..\modelfiles\<bundle>

# 3. Hand results\<slug>.answers.json to Claude Code and ask it to score
#    against SCORE_WITH_CLAUDE.md.
```

`<slug>` defaults to the bundle directory's name, lowercased, with `-` and `.`
turned into `_` (e.g. `modelfiles/Qwen3-4B-Instruct-2507` →
`qwen3_4b_instruct_2507`). Override with `--slug` or `--out`.

Full flag reference and troubleshooting: [RUN_BENCHMARK.md](RUN_BENCHMARK.md).

## Prior runs

`results/` contains finished runs collected in the `nexa-sdk` repo with the
in-process (Python-binding) harness — `Qwen3-4B-Instruct-2507`,
`Llama-v3.2-1B-Instruct`, `Llama-3.2-3B`, and several alignment/precision
variants. They remain useful as **quality** calibration references when
scoring a new run.

Treat their **performance** numbers with more care: the geniex side of those
runs went through the SDK's Python bindings rather than `auto_llm`, so TTFT and
tok/s are not strictly comparable to numbers this harness produces. Quality
scores are unaffected — the answers were generated by the same plugin over the
same bundles.

## Running genie-t2t-run by hand

The benchmark drives `genie-t2t-run` for you. To invoke it directly — e.g. to
sanity-check the QAIRT install or inspect a `--profile` file — set up the
environment and run it from the bundle directory:

```powershell
$env:QAIRT_HOME = "C:\Qualcomm\AIStack\QAIRT\2.45.0.260326"
$env:Path = "$env:QAIRT_HOME\bin\aarch64-windows-msvc;" + $env:Path
$env:Path = "$env:QAIRT_HOME\lib\aarch64-windows-msvc;" + $env:Path

# Make sure the architecture matches the device
# (v73 for X Elite, v75 for QCS8275, v81 for X2 Elite).
$env:ADSP_LIBRARY_PATH = "$env:QAIRT_HOME\lib\hexagon-v73\unsigned"

cd <repo>\modelfiles\<bundle>
genie-t2t-run.exe -c genie_config.json -p "<|im_start|>system\nYou are a helpful AI assistant.<|im_end|>\n<|im_start|>user\nWhat is France's capital?<|im_end|>\n<|im_start|>assistant\n" --profile profile.log
```

`--profile <file>` writes a `GENIE_PROFILE` JSON file with per-query KPIs
(`time-to-first-token`, `token-generation-rate`, etc.). The benchmark uses
this to record genie's TTFT / TPS; see [RUN_BENCHMARK.md](RUN_BENCHMARK.md).

## Running auto_llm by hand

The same one-shot / batch flags the benchmark uses are usable directly:

```pwsh
# One prompt, metrics to a JSON file.
.\build\bin\Release\auto_llm.exe `
    --model-dir .\modelfiles\<bundle> `
    --prompt "What is gravity?" `
    --metrics-json out.json

# Interactive REPL (no --prompt / --batch-file).
.\build\bin\Release\auto_llm.exe --model-dir .\modelfiles\<bundle> --verbose
```

See [examples/auto_llm/README.md](../examples/auto_llm/README.md) for the full
flag list.
